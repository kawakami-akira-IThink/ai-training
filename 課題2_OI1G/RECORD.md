| 観点 | メモ |
|------|------|
| spec で明確になったこと | ・顧客を特定する **id** が下書きになく、変更・削除の対象を指定できなかった<br>・「全項目一致はエラー」は**重複登録の禁止**のことで、変更にも適用すると決めた<br>・ロックは「ロック用の API」ではなく、**DB トランザクション**で行うと決めた<br>・各項目の上限（名前・仕事は256文字、年齢は1000まで、性別は male / female）<br>・検索は「完全一致の AND」で、全件は返さない<br>・エラーの形式（HTTP ステータス＋コード）<br>・下書きの受入基準は**異常系だけで、正常系がなかった** |
| AI が補完した前提（【AI補完】印の箇所） | ・SQLite には行ロックがないので、`BEGIN IMMEDIATE` で **DB 全体をロック**する（そのため、別の顧客の変更も `LOCKED` になる）<br>・ログの暗号化は Fernet（共通鍵）を使い、鍵は環境変数で渡す<br>・何も変わらない変更は重複エラーにしない<br>・認証の固定値はコードに直接書かず、環境変数から読む<br>・正常系の受入基準（登録・変更・削除のあとに検索で確かめる）<br>・`LOCKED` と `DUPLICATE` を別のエラーコードにする |
| セキュリティ観点で見つかった点 | ・**[高] 検索条件（氏名）がアクセスログに平文で残る**：URL のクエリはサーバー（uvicorn）が記録するため。アプリ側でログを暗号化しても漏れる → 検索を POST に変更<br>・粗い条件（性別だけ）で全員分が取れる → 検索では `name` を必須にした<br>・巨大な id で 500 エラー、`/docs` に認証なしで入れる、空白だけの名前が登録できる → 修正<br>・IDOR（誰でも任意の id を操作できる）、権限の区別がない、DB が平文 → OAuth 導入時に対応する前提で受容<br>・依存ライブラリのバージョン固定が直接依存だけで、**推移的依存が固定されていなかった** → 全26パッケージを固定し、`--no-deps` でまっさらな環境から再現できることを確認 |
| 人が判断すべき未確定事項 | ・認証・認可（OAuth のスコープ、担当者ごとのアクセス制御）<br>・ログ暗号化鍵の管理（保管場所、ローテーション、復号できる人の限定）<br>・DB の暗号化と、本番で行ロックが必要かどうか（SQLite のままでよいか）<br>・ログの出力先（今回は標準出力だけ。本来はファイルなど）<br>・レート制限（今回は対応しない） |
| 業務で試せそうな題材 | ✏️（例）既存のマスタ系 API について、仕様書を受入基準つきで書き直し、AI にセキュリティレビューさせる／依存ライブラリの固定状況をチェックする |

## 気づき（任意）✏️
- 自分で書いた下書きは、「自分の頭の中では当たり前のこと」（id、正常系）が抜けていた。AI の質問で気づけた。
- AI の提案は「推奨案」として出てくるので、**そのまま採用せず、意図と違う点は指摘する**必要があった（ロック方式、認証の位置づけ、依存の固定範囲）。
- セキュリティレビューは、コードを読むだけでなく**実際に動かして確かめた**指摘（500 エラー、ログ漏れ）のほうが説得力があった。
