# PBI（プロダクトバックログ）: 在庫管理システム

総務部が扱う日用品（文具・消耗品など）の品目と在庫数を管理するシステムのPBIです。
技術スタック: バックエンド Python (FastAPI) + SQLite / フロントエンド React + TypeScript (Vite)

## 凡例

| 記号 | 意味 |
|---|---|
| 【受講者】 | system_setting.md の「受入条件の下書き」に受講者が書いた条件を、Given-When-Then に清書したもの |
| 【AI補完】 | AIが新たに補った、または曖昧な点を明確化した条件。受講者による妥当性の検証が必要 |

## PBI一覧

| ID | タイトル |
|---|---|
| PBI-1 | 品目と在庫数の一覧を表示する |
| PBI-2 | 品目を追加する |
| PBI-3 | 品目を削除する |
| PBI-4 | 在庫数を増減する |

---

## PBI-1: 品目と在庫数の一覧を表示する

### ユーザーストーリー
- **Who**: 総務担当者として
- **What**: 登録済みの全品目とその現在在庫数を一覧で確認したい
- **Why**: 日用品の在庫を常に正しく把握し、補充の要否を判断するため

### 受入条件

**正常系**

1. 【受講者】画面更新時のDB一致
   - Given: DBに品目と在庫数が登録されている
   - When: 利用者が画面を開く、またはブラウザで画面を更新（リロード）する
   - Then: DBに登録されている全品目の品目名と在庫数が、DBの内容と一致して一覧に表示される

2. 【受講者】マイナス在庫の赤文字表示
   - Given: 在庫数が0未満（例: -3）の品目が存在する
   - When: 一覧を表示する
   - Then: その品目の在庫数がマイナス値のまま赤文字で表示され、通常の在庫数（黒文字等）と明確に区別できる

3. 【AI補完】品目が0件の場合
   - Given: 品目が1件も登録されていない
   - When: 一覧を表示する
   - Then: エラーにはならず、「品目がありません」等の空状態メッセージが表示される

4. 【AI補完】表示順
   - Given: 複数の品目が登録されている
   - When: 一覧を表示する
   - Then: 品目は登録順（ID昇順）で表示される（並び順は更新の前後で変わらない）

**異常系**

5. 【AI補完】一覧取得の失敗
   - Given: サーバがエラー（500等）を返す、または接続できない
   - When: 一覧を取得する
   - Then: 画面にエラーメッセージ（トースト）が表示され、直前に表示していた一覧は維持される

## PBI-2: 品目を追加する

### ユーザーストーリー
- **Who**: 総務担当者として
- **What**: 新しい日用品の品目を名称と初期在庫数を指定して登録したい
- **Why**: 新たに取り扱う日用品も在庫管理の対象に加え、在庫を漏れなく把握するため

### 受入条件

**正常系**

1. 【AI補完】品目の登録
   - Given: 同一名称の品目が未登録である
   - When: 利用者が有効な品目名（例: 「ボールペン（黒）」）と初期在庫数（0以上の整数、例: 10）を入力して追加する
   - Then: 品目が登録され（201）、一覧に新しい品目が指定した在庫数で表示される

2. 【AI補完】初期在庫数の省略
   - Given: 有効な品目名が入力されている
   - When: 初期在庫数を省略して追加する
   - Then: 初期在庫数は0として登録される

**異常系**

3. 【受講者】同一名称の登録エラー
   - Given: 品目「ボールペン（黒）」が既に登録されている
   - When: 同じ名称「ボールペン（黒）」で品目を追加しようとする
   - Then: 登録は行われず、重複エラー（409）が返り、画面にエラーメッセージが表示される。既存の品目は変更されない

4. 【AI補完】同一名称の判定ルール
   - Given: 品目「ボールペン（黒）」が既に登録されている
   - When: 前後に空白を付けた「 ボールペン（黒） 」、または大文字小文字違いの名称（英字の場合。例: 「USB」と「usb」）で追加しようとする
   - Then: 前後の空白を除去した上で、大文字小文字を区別せず比較し、同一名称とみなして重複エラーとなる

5. 【AI補完】品目名が空
   - Given: 追加フォームを開いている
   - When: 品目名が未入力、または空白文字のみで追加する
   - Then: 登録は行われず、入力エラー（400）となり、品目名が必須であることがメッセージで示される

6. 【AI補完】品目名が長すぎる
   - Given: 追加フォームを開いている
   - When: 品目名が上限（100文字）を超えて追加する
   - Then: 登録は行われず、入力エラー（400）となる

7. 【AI補完】初期在庫数が不正
   - Given: 追加フォームを開いている
   - When: 初期在庫数に整数以外（小数、文字列）または負の値を指定して追加する
   - Then: 登録は行われず、入力エラー（400）となる（初期在庫数は0以上の整数のみ。マイナス在庫は増減の結果としてのみ発生しうる）

## PBI-3: 品目を削除する

### ユーザーストーリー
- **Who**: 総務担当者として
- **What**: 取り扱いをやめた品目を一覧から削除したい
- **Why**: 不要な品目を整理し、一覧を見やすく、在庫情報を正確に保つため

### 受入条件

**正常系**

1. 【AI補完】品目の削除
   - Given: 品目が登録されている
   - When: 利用者がその品目を削除する
   - Then: 品目がDBから削除され、一覧から消える。他の品目には影響しない

2. 【AI補完】削除前の確認
   - Given: 一覧に品目が表示されている
   - When: 利用者が削除操作を行う
   - Then: 確認ダイアログが表示され、利用者が承諾した場合のみ削除が実行される（キャンセル時は何も変更されない）

3. 【AI補完】在庫が残っている品目の削除
   - Given: 在庫数が0でない品目（マイナス在庫を含む）が存在する
   - When: その品目を削除する
   - Then: 在庫数にかかわらず削除できる

**異常系**

4. 【AI補完】存在しない品目の削除
   - Given: 指定した品目IDが存在しない（他の利用者が先に削除した場合を含む）
   - When: その品目IDで削除を要求する
   - Then: 404 が返り、画面にエラーメッセージ（トースト）が表示された上で最新の一覧が再取得される

## PBI-4: 在庫数を増減する

### ユーザーストーリー
- **Who**: 総務担当者として
- **What**: 品目ごとに入庫・出庫に応じて在庫数を増減したい
- **Why**: 実際の在庫と画面上の在庫数を一致させ、常に正しい在庫を把握するため

### 受入条件

**正常系**

1. 【AI補完】在庫の増加
   - Given: 品目の在庫数が10で、画面の表示も10である
   - When: 利用者が +5 を指定して在庫を増減する（expected_quantity=10 を送信）
   - Then: 在庫数が15に更新され（200）、更新後の品目情報が返り、画面に15と表示される

2. 【AI補完】在庫の減少
   - Given: 品目の在庫数が10で、画面の表示も10である
   - When: 利用者が -3 を指定して在庫を増減する（expected_quantity=10 を送信）
   - Then: 在庫数が7に更新され、画面に7と表示される

3. 【受講者】マイナス在庫の許容
   - Given: 品目の在庫数が2で、画面の表示も2である
   - When: 利用者が -5 を指定して在庫を増減する（expected_quantity=2 を送信）
   - Then: エラーにはならず在庫数は -3 に更新され、画面には赤文字で -3 と表示される

**異常系**

4. 【受講者】画面とサーバの在庫数の不一致
   - Given: サーバ上の品目の在庫数が、画面が保持している在庫数（expected_quantity）と異なる（他の利用者が先に更新した場合等）
   - When: 利用者が在庫の増減を実行する（リクエストに expected_quantity を含める）
   - Then: サーバは在庫を更新せず 409 Conflict と最新の品目情報を返す。画面はトーストでエラーメッセージを表示し、最新の状態を再取得して画面に反映する

5. 【AI補完】増減量が不正
   - Given: 在庫増減の入力欄が表示されている
   - When: 増減量が 0、整数以外（小数、文字列）、または未指定で実行する
   - Then: 在庫は更新されず、入力エラー（400）となる（増減量は 0 以外の整数のみ有効）

6. 【AI補完】expected_quantity が未指定または不正
   - Given: 在庫増減のリクエストが送信される
   - When: expected_quantity が未指定、または整数でない
   - Then: 在庫は更新されず、入力エラー（400）となる

7. 【AI補完】存在しない品目の増減
   - Given: 指定した品目IDが存在しない（他の利用者が先に削除した場合を含む）
   - When: その品目IDで在庫増減を要求する
   - Then: 404 が返り、画面にエラーメッセージ（トースト）が表示された上で最新の一覧が再取得される

## 共通の受入条件（非機能・横断）

全PBIに共通して適用する条件です。

1. 【受講者】レスポンス時間
   - Given: 全ての操作（一覧表示・追加・削除・増減）が対象である
   - When: いずれかの操作のAPIを呼び出す
   - Then: レスポンスが0.2秒以内に返る

2. 【AI補完】レスポンス時間の測定条件
   - Given: ローカル環境（サーバとクライアントが同一マシン）で、DBに品目が100件登録されている
   - When: 各操作のAPIを1回呼び出し、リクエスト送信からレスポンス受信完了までを測定する
   - Then: 全ての操作で0.2秒（200ms）以内である（ネットワーク遅延は含まない）

3. 【受講者】操作後の再取得
   - Given: 利用者が追加・削除・在庫増減のいずれかの操作を行う
   - When: 操作が完了する（成功・失敗を問わない）
   - Then: 画面は在庫情報（品目一覧）をサーバから再取得し、画面表示を最新の状態に更新する

4. 【受講者】画面更新時のDB一致
   - PBI-1 の受入条件1 を参照（画面を更新した時、DBの品目・在庫数が画面に正しく表示される）

5. 【AI補完】エラー表示の統一
   - Given: いずれかの操作がエラー（400/404/409/500等）となる
   - When: 画面がエラーレスポンスを受け取る
   - Then: エラー内容が利用者に分かるメッセージとしてトースト表示され、画面の状態はサーバの最新状態と一致する

## 未確定事項（受講者の判断が必要な点）

- 品目名の最大文字数（本書では100文字と仮置き）
- 同一名称判定のルール（本書では「前後空白を除去・大文字小文字を区別しない」と仮置き。全角/半角の違いは区別するか）
- 同一名称登録時のステータスコード（本書では 409 と仮置き。400 とするか）
- 初期在庫数の扱い（本書では「省略可・省略時0・0以上の整数」と仮置き。必須にするか、初期値でのマイナスを許容するか）
- 増減量の上限・下限（本書では0以外の整数のみとし、上限は未設定。極端に大きな値を拒否するか）
- 削除前の確認ダイアログの要否（本書では確認ありと仮置き）
- 在庫が0でない品目の削除を許可してよいか（本書では許可と仮置き）
- 一覧の並び順（本書では登録順と仮置き。品目名順などにするか）
- 0.2秒の測定条件（本書ではローカル環境・100件と仮置き。実運用の件数・環境に合わせるか）
- 共通条件3「失敗時も再取得」の範囲（本書では成功・失敗問わず再取得と解釈。エラー時は再取得しない選択もありうる）
- 同時に複数の利用者が操作する想定の有無（409の発生頻度や運用に影響）
